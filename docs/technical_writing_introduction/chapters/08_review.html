第 8 章 レビューと保守

書き上げた文書には、書き手が気付かない誤りや分かりにくい箇所が必ず残っている。また、公開した文書は、対象のソフトウェアが変わるにつれて古くなる。本章では、文書をレビューする方法と、公開後も正しい状態に保つ方法を説明する。

セルフレビュー

他者にレビューを依頼する前に、書き手自身が文書を見直す。セルフレビューでは、次の方法が効果的である。

  • 時間をおく：書いた直後は、書いた内容を覚えているため、文章の分かりにくさに気付きにくい。少なくとも数時間、できれば一晩おいてから読み直す。

  • 読者になりきる：「第 2 章 書く前の準備」で定めた読者の前提知識だけで理解できるかを確かめる。手順書であれば、実際に手順どおりに操作する。

  • 声に出して読む：音読すると、長すぎる文やリズムの悪い文、助詞の誤りに気付きやすい。

  • 表示形式を変える：エディターで書いた文書を、ビルド後の HTML や印刷物で読み直すと、見落としていた誤りに気付くことがある。

確認する観点は、「付録 A チェックリスト」にまとめた。

他者によるレビュー

書き手にとって自明なことは、読者にとって自明とは限らない。書き手自身では見つけられない問題を見つけるために、他者にレビューを依頼する。

レビューを依頼するときは、次の情報を伝える。

  • 文書の目的と想定する読者

  • 特に見てほしい観点（たとえば「技術的に正しいか」「初心者が手順どおりに作業できるか」）

  • レビューの期限

レビュアーには、想定する読者に近い人を選ぶとよい。初心者向けのチュートリアルを、その分野の専門家だけがレビューすると、初心者がつまずく箇所を見落としやすい。

レビューで指摘するときは、次の点に注意する。

  • 問題の箇所と、なぜ問題なのかを具体的に書く。

  • 可能であれば、修正の案を示す。

  • 必ず直してほしい指摘と、提案にとどまる指摘を区別する。たとえば、指摘の先頭に「必須」「提案」「質問」のような区分を付ける。

指摘を受ける書き手は、読者の誤解を書き手の責任と考える。レビュアーが誤解した箇所は、ほかの読者も誤解する可能性が高い。

ツールによる検査

表記ゆれや長すぎる文のように、機械的に判定できる問題は、人が目で探すよりもツールで検査するほうが確実である。人のレビューは、ツールでは判定できない問題（内容の正しさや構成の妥当性）に集中させる。

ソースコードを次に示す。ファイルは check_style.py からダウンロードできる。実行には Python 3.10 以降が必要である。

  1"""日本語の技術文書を対象とした簡易文章チェッカー。
  2
  3次の 4 種類の問題を検出し、「ファイル名:行番号:列番号: [規則名] メッセージ」の形式で出力する。
  4
  5* long-sentence: 一文（句点「。」で区切った範囲）が指定した文字数を超えている。
  6* spacing: 日本語の文字と英数字の間に半角空白がない。
  7* variant: 本書の表記規則と異なる表記（表記ゆれ）がある。
  8* vague: 曖昧な表現がある。
  9
 10Markdown のコードブロック（``` で囲まれた範囲）とインラインコード（` で囲まれた範囲）は検査しない。
 11一文の長さは行単位で数えるため、一文を複数の行に分けて書いている文書では正しく数えられない。
 12
 13使い方:
 14    python check_style.py 文書.md [文書.md ...] [--max-length 文字数]
 15
 16問題が見つかった場合は終了コード 1 を、ファイルを読めなかった場合は終了コード 2 を返す。
 17"""
 18
 19import argparse
 20import re
 21import sys
 22from collections.abc import Iterator, Sequence
 23from dataclasses import dataclass
 24from pathlib import Path
 25
 26DEFAULT_MAX_LENGTH = 80
 27
 28# 日本語の文字（ひらがな、カタカナ、長音記号、漢字、「々」）と英数字
 29JAPANESE = r"[ぁ-ゖァ-ヺー一-鿿々]"
 30ALNUM = r"[A-Za-z0-9]"
 31
 32# 日本語の直後の英数字、または英数字の直後の日本語に一致する
 33MISSING_SPACE = re.compile(f"(?<={JAPANESE}){ALNUM}|(?<={ALNUM}){JAPANESE}")
 34
 35# インラインコード（`code` や ``code``）
 36INLINE_CODE = re.compile(r"`+[^`]*`+")
 37
 38# (検出する表記, 推奨する表記)
 39VARIANT_RULES: tuple[tuple[re.Pattern[str], str], ...] = (
 40    (re.compile(r"サーバ(?!ー)"), "サーバー"),
 41    (re.compile(r"ユーザ(?![ービ])"), "ユーザー"),
 42    (re.compile(r"出来(?=[るなま])"), "でき"),
 43    (re.compile(r"全て"), "すべて"),
 44    (re.compile(r"下さい"), "ください"),
 45)
 46
 47VAGUE_WORDS: tuple[str, ...] = ("適宜", "なるべく", "できるだけ", "しばらく", "高速に")
 48
 49
 50@dataclass(frozen=True)
 51class Issue:
 52    """検出した問題を 1 件表す。"""
 53
 54    path: str
 55    line: int
 56    column: int
 57    rule: str
 58    message: str
 59
 60    def format(self) -> str:
 61        """コンパイラーの警告と同じ形式の文字列にする。"""
 62        return f"{self.path}:{self.line}:{self.column}: [{self.rule}] {self.message}"
 63
 64
 65def mask_inline_code(line: str) -> str:
 66    """インラインコードを同じ長さの空白に置き換える（列番号を変えないため）。"""
 67    return INLINE_CODE.sub(lambda match: " " * len(match.group(0)), line)
 68
 69
 70def iter_target_lines(text: str) -> Iterator[tuple[int, str]]:
 71    """検査対象の行を (行番号, 行) の組で返す。コードブロックの中の行は返さない。"""
 72    in_code_block = False
 73    for number, line in enumerate(text.splitlines(), start=1):
 74        if line.lstrip().startswith("```"):
 75            in_code_block = not in_code_block
 76            continue
 77        if not in_code_block:
 78            yield number, mask_inline_code(line)
 79
 80
 81def check_sentence_length(path: str, number: int, line: str, max_length: int) -> Iterator[Issue]:
 82    """一文の長さを検査する。"""
 83    start = 0
 84    for sentence in line.split("。"):
 85        length = len(sentence.strip())
 86        if length > max_length:
 87            column = start + len(sentence) - len(sentence.lstrip()) + 1
 88            message = f"一文が {length} 文字ある（上限 {max_length} 文字）。文を分けられないか検討する。"
 89            yield Issue(path, number, column, "long-sentence", message)
 90        start += len(sentence) + 1
 91
 92
 93def check_spacing(path: str, number: int, line: str) -> Iterator[Issue]:
 94    """日本語と英数字の間の半角空白を検査する。"""
 95    for match in MISSING_SPACE.finditer(line):
 96        yield Issue(path, number, match.start() + 1, "spacing", "日本語と英数字の間に半角空白を入れる。")
 97
 98
 99def check_variants(path: str, number: int, line: str) -> Iterator[Issue]:
100    """表記ゆれを検査する。"""
101    for pattern, preferred in VARIANT_RULES:
102        for match in pattern.finditer(line):
103            message = f"「{match.group(0)}」は「{preferred}」と書く。"
104            yield Issue(path, number, match.start() + 1, "variant", message)
105
106
107def check_vague_words(path: str, number: int, line: str) -> Iterator[Issue]:
108    """曖昧な表現を検査する。"""
109    for word in VAGUE_WORDS:
110        for match in re.finditer(re.escape(word), line):
111            message = f"曖昧な表現「{word}」がある。条件や数値で具体的に書けないか検討する。"
112            yield Issue(path, number, match.start() + 1, "vague", message)
113
114
115def check_text(path: str, text: str, max_length: int = DEFAULT_MAX_LENGTH) -> list[Issue]:
116    """文書全体を検査し、見つかった問題を行番号と列番号の順に並べて返す。"""
117    issues: list[Issue] = []
118    for number, line in iter_target_lines(text):
119        issues.extend(check_sentence_length(path, number, line, max_length))
120        issues.extend(check_spacing(path, number, line))
121        issues.extend(check_variants(path, number, line))
122        issues.extend(check_vague_words(path, number, line))
123    return sorted(issues, key=lambda issue: (issue.line, issue.column))
124
125
126def parse_args(argv: Sequence[str] | None) -> argparse.Namespace:
127    """コマンドライン引数を解析する。"""
128    parser = argparse.ArgumentParser(description="日本語の技術文書を対象とした簡易文章チェッカー")
129    parser.add_argument("paths", nargs="+", type=Path, help="検査する文書（UTF-8）")
130    parser.add_argument(
131        "--max-length",
132        type=int,
133        default=DEFAULT_MAX_LENGTH,
134        help=f"一文の文字数の上限（既定値: {DEFAULT_MAX_LENGTH}）",
135    )
136    return parser.parse_args(argv)
137
138
139def main(argv: Sequence[str] | None = None) -> int:
140    """エントリーポイント。終了コードを返す。"""
141    args = parse_args(argv)
142    found = False
143    for path in args.paths:
144        try:
145            text = path.read_text(encoding="utf-8")
146        except (OSError, UnicodeDecodeError) as error:
147            print(f"{path}: ファイルを読めない: {error}", file=sys.stderr)
148            return 2
149        for issue in check_text(str(path), text, args.max_length):
150            print(issue.format())
151            found = True
152    return 1 if found else 0
153
154
155if __name__ == "__main__":
156    sys.exit(main())

検査の対象として、問題を含む Markdown 文書 sample_bad.md を用意した。

 1# ログ解析ツールの使い方
 2
 3本ツールはサーバのログを解析し、エラーが見つかった場合は管理者にメールで通知するが、設定ファイルが存在しない場合は既定値を使用し、その場合は警告を出力するので注意して下さい。
 4
 5解析には Python3.12以降が必要である。
 6
 7ログが大きい場合は、適宜ファイルを分割してから実行する。
 8
 9全ての処理が終わるまで、しばらく待つ。
10
11```
12python analyze.py --input サーバ.log
13```
14
15インラインコード `python analyze.py` の中も検査しない。

次のコマンドで検査する。

1$ python check_style.py sample_bad.md

出力は次のとおりである。各行は「ファイル名:行番号:列番号: [規則名] メッセージ」の形式で、問題の位置と内容を示す。11～13 行目のコードブロックと、15 行目のインラインコードの中は検査の対象外である。

1sample_bad.md:3:1: [long-sentence] 一文が 86 文字ある（上限 80 文字）。文を分けられないか検討する。
2sample_bad.md:3:6: [variant] 「サーバ」は「サーバー」と書く。
3sample_bad.md:3:84: [variant] 「下さい」は「ください」と書く。
4sample_bad.md:5:16: [spacing] 日本語と英数字の間に半角空白を入れる。
5sample_bad.md:7:11: [vague] 曖昧な表現「適宜」がある。条件や数値で具体的に書けないか検討する。
6sample_bad.md:9:1: [variant] 「全て」は「すべて」と書く。
7sample_bad.md:9:13: [vague] 曖昧な表現「しばらく」がある。条件や数値で具体的に書けないか検討する。

このチェッカーは、規則の考え方を示すための簡易的な実装である。たとえば一文の長さは行単位で数えるため、一文を複数の行に分けて書いた文書では正しく数えられない。実際のプロジェクトでは、textlint のような実績のあるツールを使うとよい。

Docs as Code

文書をソースコードと同じ方法で管理する考え方を Docs as Code と呼ぶ。具体的には、次のように運用する。

  • 文書を Markdown や reStructuredText のようなテキスト形式で書く。

  • 文書を Git のようなバージョン管理システムで管理する。

  • 文書の変更も、プルリクエストを通じてレビューする。

  • CI（継続的インテグレーション）で、文書のビルド、文章校正ツールによる検査、リンク切れの検査を自動的に実行する。

文書をソースコードと同じリポジトリに置くと、コードの変更と文書の変更を同じプルリクエストで扱える。その結果、文書の更新漏れをレビューで見つけやすくなる。本書も、reStructuredText で書いた文書を Sphinx でビルドしている。

文書の陳腐化を防ぐ

文書は、公開した時点から古くなり始める。誤った情報を含む文書は、文書がない状態よりも害が大きい。読者は文書を信じて行動するためである。文書を正しい状態に保つために、次のことを行う。

  • 担当者を決める：文書ごとに更新の責任を持つ担当者やチームを決め、文書に明記する。

  • 最終更新日と対象バージョンを書く：読者が、その文書が現在も有効かどうかを判断できるようにする。

  • 更新を作業の完了条件に含める：仕様を変更するプルリクエストでは、関連する文書の更新も完了条件にする。プルリクエストのテンプレートに確認項目を設けると、更新漏れを防ぎやすい。

  • 定期的に見直す：たとえば四半期に一度、文書の一覧を確認し、古くなった文書を更新する。

  • 不要な文書を削除する：使われなくなった文書は削除するか、古い文書であることを冒頭に明記して保管する。
