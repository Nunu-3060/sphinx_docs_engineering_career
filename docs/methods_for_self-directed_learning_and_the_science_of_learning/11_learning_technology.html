第 11 章 技術を学ぶ実践

第 I 部と第 II 部では、学習と記憶の仕組み、効果が確かめられた学習法、理解と転移、熟達化などの理論を扱った。第 III 部では、これらの理論をエンジニアの独学に当てはめる。本章では、新しいプログラミング言語、フレームワーク、ライブラリ、クラウドサービスなどの技術そのものを身に付ける方法を扱う。

技術の学習には、概念を理解すること、コードを書けるようになること、問題が起きたときに原因を突き止められるようになることが含まれる。本章ではこの順に、全体像の把握、例題から自力解決への移行、写経と改変、小さなプロジェクト、コードリーディング、デバッグを取り上げ、最後に数学などの前提知識が必要な高度な技術に取り組む方法を述べる。

新しい技術の全体像をつかむ

なぜ全体像が必要か

新しい技術を学び始めるとき、多くの人はチュートリアルの最初から順に進める。しかし、全体像を持たないまま細部を学ぶと、個々の知識がどこに位置づくのか分からず、知識が断片のまま残りやすい。

第 3 章 学習と記憶の仕組み で述べたように、長期記憶の知識はスキーマとして構造化されている。全体像は、これから学ぶ知識を配置するための枠組み、いわば仮のスキーマとして働く。最初に大まかな枠組みを作っておくと、後から学ぶ細部を既存の構造に結び付けやすくなり、作業記憶の負担も減る。

全体像をつかむ手順

次の手順は、新しい技術に最初の数時間で取り組む際の目安である。

  1. 学ぶ目的を一文で書く。「社内の API を FastAPI で書き直すため」「論文の手法を PyTorch で再現するため」のように、何に使うかを明確にする。目的によって、深く学ぶべき部分と、名前だけ知っていればよい部分が変わる。

  2. 公式ドキュメントの構成を眺める。目次を見て、チュートリアル、ガイド、API リファレンス、概念の解説がそれぞれどこにあるかを確認する（ドキュメントの構成と読み方は 第 12 章 読む技術: ドキュメント・書籍・論文 で扱う）。

  3. その技術が解決する問題を調べる。公式サイトの概要や「なぜこの技術を使うのか」に当たる説明を読み、既存の技術と比べて何が違うのかを把握する。

  4. 主要な概念を 10 個程度書き出す。ドキュメントの目次や概要に繰り返し現れる用語を拾う。例えば Kubernetes なら Pod、Deployment、Service、Namespace などである。

  5. 概念同士の関係を図にする。どの概念がどの概念を含むか、どの概念がどの概念を使うかを、矢印でつないだ簡単な図（概念マップ）にする。

  6. 最小の動作例を動かす。公式のクイックスタートなどで、とにかく一度動かしてみる。ここでは理解よりも、全体の流れを体験することを優先する。

手順 5 で作る概念マップは、最初は不正確でかまわない。学習が進むにつれて書き直すこと自体が、理解を深める作業になる。以下に、Web フレームワークを学び始めたときの概念マップの例を示す。

例題から自力解決へ

ワークドエグザンプルの効果

ワークドエグザンプル（worked example）とは、問題とその解き方を順を追って示した例題である。Sweller と Cooper [SwellerCooper1985] は、代数の学習で、問題を自力で解くよりもワークドエグザンプルを学ぶ方が、学習が効率的になることを示した。

この結果は、第 3 章 学習と記憶の仕組み で扱った認知負荷理論で説明できる。初心者が問題を自力で解こうとすると、目標と現状の差を縮める手段を手探りで探すことに作業記憶の大部分が使われ、解き方のパターン（スキーマ）を学ぶための余裕が残らない [Sweller1988]。ワークドエグザンプルは、この探索の負担を取り除き、解き方そのものに注意を向けさせる。

ただし、ワークドエグザンプルを読むだけでは、読んだつもりになって終わるおそれがある。例題の各手順について「なぜこの手順なのか」を自分に説明する自己説明（第 4 章 効果が確かめられた学習法 で扱った）を組み合わせると効果が高まる [Chi1989]。

フェーディング

ワークドエグザンプルは初心者には有効であるが、いつまでも例題ばかり学んでいては、自力で解ける力は付かない。Renkl と Atkinson [Renkl2003] は、完全なワークドエグザンプルから始め、例題の手順を一つずつ空欄にした部分完成問題（completion problem）に移り、最終的に自力解決に至るように、支援を段階的に減らしていく方法を提案した。これをフェーディング（fading）と呼ぶ。

根拠の強さ: 強い

初心者にとってワークドエグザンプルが問題解決よりも効率的であることは、数学、物理、プログラミングなど多くの領域で繰り返し示されている。フェーディングの効果も複数の研究で確認されている。

Python による具体例

ここでは、Python の辞書を使って要素の出現回数を数えるという課題を例に、フェーディングを具体的に示す。

最初の段階は、ワークドエグザンプルである。コードの各行に、なぜその処理が必要かを説明するコメントを付けている。学習者はコードを読みながら、各行の役割を自分の言葉で説明してみる。

コード 3 段階 1: ワークドエグザンプル（単語の出現回数を数える）
 1def count_words(words: list[str]) -> dict[str, int]:
 2    # 単語をキー、出現回数を値とする辞書を用意する。
 3    counts: dict[str, int] = {}
 4    for word in words:
 5        # 初めて現れた単語は get() が既定値 0 を返すので、1 から数え始められる。
 6        counts[word] = counts.get(word, 0) + 1
 7    return counts
 8
 9
10print(count_words(["apple", "banana", "apple"]))  # {'apple': 2, 'banana': 1}

 5        initial = word[0]

11print(group_by_initial(["apple", "avocado", "banana"]))  # {'a': ['apple', 'avocado'], 'b': ['banana']}

空欄の答えは 7 行目の [] と word である。段階 1 の get() と段階 2 の setdefault() は、どちらも「キーがなければ既定値を使う」という同じ考え方に基づいている。この共通点に気付くことが、個別のメソッドの暗記を超えて、辞書を使った集計のパターン（スキーマ）を身に付けることにつながる。

最後の段階は、自力解決である。問題だけを示し、解き方は示さない。

コード 5 段階 3: 自力解決の問題
1アクセスログの各行は「日時 ユーザー名 URL」の形式で書かれている。
2ログの行のリストを受け取り、ユーザーごとのアクセス回数を数え、
3アクセス回数の多い順に上位 3 人を返す関数を書け。
4型ヒントを付け、ログが空の場合にも正しく動くこと。

この問題では、段階 1 の集計のパターンに加えて、文字列の分割と並べ替えが必要になる。学んだパターンを、少し異なる状況で使えるかどうかを確かめることで、第 6 章 理解と転移 で扱った転移の力も養われる。

熟達化反転効果

ワークドエグザンプルは、いつでも、誰にでも有効なわけではない。Kalyuga ら [Kalyuga2003] は、初心者に有効な支援が、知識を身に付けた学習者にとっては効果がなくなり、かえって学習を妨げる場合があることを示し、これを熟達化反転効果（expertise reversal effect）と呼んだ。すでにパターンを理解している学習者にとって、丁寧な解説は冗長な情報であり、それを処理すること自体が余計な負荷になるためである。

これは、学習者が自分の習熟度に応じて教材を選ぶ必要があることを意味する。次の表は、習熟度に応じた教材の選び方の目安である。

表 17 習熟度に応じた教材の選び方

習熟度

状態

適した教材・学び方

初級の学習者

用語や基本的な構文がまだ分からない

中級の学習者

基本は分かるが、自力で設計するのは難しい

チュートリアルが冗長で退屈に感じるようになったら、それは次の段階に進む合図である。反対に、自力解決の問題で長時間手が止まるなら、一段階前の教材に戻るとよい。

なお、先に自力で問題に取り組んで失敗してから解き方を学ぶ生産的失敗（第 4 章 効果が確かめられた学習法）は、ワークドエグザンプルの研究と一見矛盾するが、自力で取り組む時間の後に必ず解き方の指導が続くことを前提としている。指導をまったく伴わない発見学習が初心者には効果が低いことは 第 2 章 独学とは何か で述べた。独学で手探りの試行錯誤をする場合も、一定時間取り組んだら解説や解答を確認する、という区切りを設けるとよい。

写経と改変

写経の効果と限界

写経とは、書籍やチュートリアルのコードを自分の手で入力することである。写経は、構文に慣れる、エラーメッセージに出会う、開発環境の使い方を覚える、といった初期段階では役に立つ。

しかし、写経は考えなくてもできてしまう作業でもある。コードを一文字ずつ書き写しているだけでは、第 4 章 効果が確かめられた学習法 で扱った再読と同じく、内容を処理する深さが浅くなりやすい。写経をするなら、次のように頭を使う工夫を加えるとよい。

  • 書き写す前に、そのコードが何をするかを予想する。

  • 数行ごとに、なぜその書き方なのかを自分に説明する。

  • 見本を見ずに、思い出しながら書いてみる。

改変による学習

写経の後は、コードを改変する段階に進む。改変とは、動くコードを出発点にして、仕様を変えたり、機能を追加したりすることである。例えば、チュートリアルの TODO アプリに期限の機能を加える、出力形式を JSON から CSV に変える、といった変更を加える。

改変では、自分で答えを作り出す必要がある。自分で生成した情報は、読んだだけの情報より記憶に残りやすい（生成効果、第 4 章 効果が確かめられた学習法）。改変は、既存のコードという足場の上で生成を行う、初心者にも取り組みやすい学習活動である。

改変の課題は、次のように小さなものから始めるとよい。

  1. 定数や文字列を変える（変更がどこに反映されるかを確かめる）。

  2. 条件や繰り返しを変える（処理の流れを理解しているかを確かめる）。

  3. 関数を一つ追加する（既存の構造に合わせた設計ができるかを確かめる）。

  4. 新しい機能を追加する（複数の部品の連携を理解しているかを確かめる）。

小さなプロジェクトによる学習

改変に慣れたら、小さなプロジェクトを自分で一から作る。プロジェクトには、チュートリアルにはない次のような学習機会がある。

  • 何を作るかを決めるところから始めるため、設計の判断が必要になる。

  • チュートリアルで扱われない問題に必ず出会い、調べる力が鍛えられる。

  • 完成したときに成果物が残り、第 9 章 動機づけと習慣 で扱った有能感が得られる。

プロジェクトの規模は、数日から 2 週間程度で完成できる大きさにする。大きすぎると完成までの期間が長くなり、途中で挫折しやすい。また、プロジェクトの中で、学びたい技術の主要な概念を使うように設計する。例えば、非同期処理を学ぶのが目的なら、複数の Web API から並行してデータを取得するツールを作る、といった具合である。

プロジェクトだけで学ぼうとすると、作ることに必死になり、理解が後回しになることがある。プロジェクトの途中で新しく学んだことは、第 13 章 書くこと・教えることで学ぶ で扱う方法でメモに残し、後で 第 4 章 効果が確かめられた学習法 の検索練習の題材にするとよい。

コードリーディングから学ぶ

他者が書いたコードを読むことは、熟達者の考え方を学ぶ有力な方法である。第 7 章 熟達化と意図的練習 で扱ったように、熟達者は初心者とは異なる知識の構造を持っており、その一端はコードの書き方に表れる。

ただし、規模の大きいコードを先頭から読んでも、全体の構造が見えず、細部に埋もれてしまう。次の手順で読むとよい。

  1. README とディレクトリ構成を見て、プロジェクトの目的と主要な部品を把握する。

  2. 入り口（main 関数、CLI のコマンド定義、Web アプリのルーティングなど）を見つける。

  3. 一つの機能に絞り、その機能の処理の流れを入り口から追う。

  4. 読む前に「この関数は何をしているはずか」を予想し、読んだ後に予想と比べる。

  5. テストコードを読み、関数の想定された使われ方を確認する。

  6. 理解した処理の流れを、図や文章で書き出す。

手順 4 の予想と照合は、検索練習と自己説明を組み合わせた活動である。予想が外れた箇所は、自分の理解と実際のコードがずれている箇所であり、学ぶべき点がそこにある。

デバッグを学びに変える

デバッグは、自分の理解の誤りが表に出る場面である。プログラムが期待どおりに動かないのは、多くの場合、言語やライブラリの振る舞いについての自分の理解（メンタルモデル）が実際と異なっているためである。したがって、デバッグは、誤った理解を修正する絶好の機会になる。これは 第 6 章 理解と転移 で扱った誤概念の修正にあたる。

しかし、手当たり次第にコードを変えて、たまたま動いたら終わりにすると、なぜ動かなかったのかが分からないまま終わり、学びが残らない。デバッグを学びに変えるには、仮説と検証の手順を踏み、結果を記録する。

コード 6 デバッグ記録の例
1【現象】 asyncio で並行して API を呼ぶつもりで、先にコルーチンのリストを作り、for ループの中で
2        順に await した。処理時間が逐次実行と変わらない。
3【予想】 各リクエストが並行して実行され、全体の時間は最も遅いリクエスト程度になるはず。
4【仮説 1】 コルーチンは await されるまで実行されないため、ループの中で 1 つずつ実行と完了待ちを
5         繰り返している。
6【検証 1】 asyncio.gather() でまとめて待つように変更 → 処理時間が短くなった。仮説 1 は正しい。
7【誤っていた理解】 コルーチンを作るだけで実行が始まると思っていた。実際には、await するか
8                  タスクとして登録するまで実行されない。
9【次に確かめること】 asyncio.create_task() と gather() の違い。

記録のうち、特に重要なのは「誤っていた理解」の行である。これを書き出すことで、個別のバグの修正が、言語やライブラリの仕組みについての一般的な知識に変わる。記録はそのまま、第 16 章 学習を支える仕組みとツール で扱う間隔反復のカードの題材にもなる（「コルーチンはいつ実行されるか?」）。

高度な技術に取り組む

前提知識の壁

機械学習、コンピューターグラフィックス、暗号、分散システムなどの高度な技術では、数学やアルゴリズムなどの前提知識が必要になることが多い。前提知識が不足したまま学ぼうとすると、第 9 章 動機づけと習慣 で扱った期待（できそうだという感覚）が下がり、挫折しやすい。

一方で、前提知識をすべて身に付けてから取り組もうとすると、目的の技術にたどり着く前に長い時間がかかり、学ぶ価値が見えにくくなる。Tricot と Sweller [Tricot2014] は、問題解決の力の多くは領域に固有の知識に依存しており、一般的な思考スキルを先に鍛えても、特定の領域の問題が解けるようにはなりにくいと論じている。数学一般を学んでから機械学習に進むよりも、機械学習に必要な数学を必要なときに学ぶ方が、学んだ知識が目的と結び付きやすい。

必要な前提知識を見つける

前提知識の補い方として、次の手順を勧める。

  1. 目的の技術の教材を読み進め、理解できない箇所に印を付ける。

  2. 印を付けた箇所で、何が分からないのかを特定する（用語か、数式の記法か、背景の概念か）。

  3. 分からない概念について、その概念の前提となる概念をたどる。例えば「誤差逆伝播法が分からない」→「連鎖律が分からない」→「合成関数の微分が分からない」のように、理解できる地点までさかのぼる。

  4. さかのぼった地点から、目的の箇所に戻るまでに必要な範囲だけを学ぶ。

  5. 目的の教材に戻り、印を付けた箇所を読み直す。

この方法では、前提知識の学習が常に目的の技術と結び付いているため、学ぶ価値が見えやすい。ただし、同じ分野の前提知識の不足が何度も見つかる場合は、その分野の入門書で体系的に学び直したほうが、結果的に早い場合もある。

エンジニアの独学への応用

本章の内容を、新しい技術を学ぶ際の一連の流れとしてまとめる。

  1. 最初の数時間で全体像をつかむ。学ぶ目的を書き、ドキュメントの構成を眺め、主要な概念の概念マップを作り、最小の動作例を動かす。

  2. 自分の習熟度に合った教材を選ぶ。初心者のうちはワークドエグザンプルと自己説明を組み合わせ、部分完成問題、自力解決の順に支援を減らす。

  3. 写経をするなら、予想と自己説明を加え、早めに改変に移る。

  4. 数日から 2 週間で完成できる小さなプロジェクトを作る。

  5. 他者のコードを読むときは、一つの機能に絞り、予想してから読む。

  6. デバッグでは、仮説と検証の手順を踏み、「誤っていた理解」を記録する。

  7. 高度な技術に必要な前提知識は、目的の教材から理解できる地点までさかのぼって補う。

まとめ

  • 新しい技術を学ぶときは、細部に入る前に全体像をつかむ。概念マップは、後から学ぶ知識を配置する枠組みになる。

  • 初心者にはワークドエグザンプルが有効である。フェーディングにより、部分完成問題を経て自力解決へと支援を段階的に減らす。

  • 熟達化反転効果により、初心者に有効な支援は、習熟した学習者には妨げになることがある。習熟度に応じて教材を選ぶ。

  • 写経は初期段階では役立つが、考えなくてもできてしまう。予想と自己説明を加え、改変に早く移る。

  • 小さなプロジェクトとコードリーディングは、設計の判断や熟達者の考え方を学ぶ機会になる。

  • デバッグは誤った理解を修正する機会である。仮説と検証の手順を踏み、誤っていた理解を記録する。

  • 高度な技術の前提知識は、目的の教材から必要な範囲だけさかのぼって補う。
